## 修复渲染 bug（用户试用反馈）

用户截图反馈「这是在干什么」。因视觉工具不可用，改用**用户自带的本地端点**（`deepseek-v4.1-flash-hy` 支持图像输入）以 base64 data URL 读图，成功转写截图内容。

**截图诊断**：用户从 `target/debug/` 目录启动了二进制，导致 agent 的 cwd 是构建产物目录，`list_dir "."` 列出的是 `.rlib`/`deps`/`incremental`；且程序正卡在 `? allow bash {...} [y/N]` 审批提示等待输入。

**发现的渲染 bug**：`Renderer` 中 `ThinkingDelta` 未设置 `line_open`，导致「思考文本」与后续「正文」「工具标题」粘在同一行（如 `Let me list...⚙List Directory`、`Just respond.你好！`）。

**修复**（`crates/rsagent/src/main.rs`）：`Renderer` 增 `thinking_open: bool`；`ThinkingDelta` 时若正文行开着先 `flush_line` 再置 `line_open/thinking_open`；`TextDelta` 时若思考行开着先 `flush_line`；`flush_line` 一并清 `thinking_open`。实测思考/正文/工具各占一行。

**Windows 编码问题（已知未修）**：中文 Windows 下子进程若输出 GBK 错误信息（如「系统找不到指定的路径」），`from_utf8_lossy` 会变成乱码并传给模型。彻底修复需引入 `encoding_rs` 做 GBK 回退，暂缓。

**结果**：`cargo fmt --check` 干净、clippy 0 告警、11 测试全过。

## 续：修复「看起来卡住」的审批交互（用户第二次反馈）

用户反馈「让它查看目录中的文件，然后卡那里了」。结合上一张截图定位到 **3 个问题**：

1. **根因：审批提示没走事件流**。`AgentEvent::ToolApprovalRequest/Response` 早已在 `agent.rs` 发射，但 CLI `Renderer` **没有对应渲染分支**；提示改由 `CliApprover::Ask` 直接 `eprint!` 到 stderr，与流式输出并发、交错、不醒目，看起来就像卡死。
   - 修复：`Renderer` 新增 `ToolApprovalRequest` 分支，输出 `? <tool> wants to run: {...}` + `  allow? [y/N]`（stdout，顺序正确）；`CliApprover::Ask` 只负责读输入、不再打印。

2. **双 stdin 读取器丢输入**：REPL 用 `BufReader::new(stdin).lines()`，审批器又新建一个 `BufReader::new(stdin).read_line()` —— 两个独立缓冲，前者的缓冲会吞掉后者要读的字节。
   - 修复：新增 `SharedInput = Arc<Mutex<BufReader<Stdin>>>` + `shared_stdin()` + `read_line()`，REPL 与 `CliApprover` 共用同一实例。`CliApprover` 由 `Copy` 改 `Clone`（持 Arc）。
   - 注：`tokio::io::Stdin` 不实现 `AsyncBufRead`，故不能直接 `stdin().read_line()`。

3. **审批前就显示「已开始」**：preflight 先 `emit(ToolExecutionStart)` 再 `check_approval`，导致 `⚙ Shell {...}` 出现在审批提示之前，语义误导。
   - 修复：`run_tool_calls` 调整顺序 —— **先审批，批准后才 emit `ToolExecutionStart`**；被拒的调用只产生 `ToolExecutionEnd(is_error)`，不再有误导的 `⚙` 行。

**附带**：`main()` 超长 → 抽出 `build_agent(cli, input)`。

**实测**（真实模型，管道模拟输入）：
- 允许：`? bash wants to run: {"command":"echo approval-works"}` → `  allow? [y/N]` → `⚙ Shell` → `  │ approval-works` → `✓ bash approval-works`。
- 拒绝（回车）：只出 `✗ bash tool call denied by the approval policy`，模型随即改用其他方式并如实汇报。

**结果**：`cargo fmt --check` 干净、clippy 0 告警、11 测试全过、doc 正常。

## 续：审批提示「说人话」（用户第三次反馈）

用户指出：`? bash wants to run: {...} / allow? [y/N]` 这种提示对不懂命令行的人等于黑话，要求**按具体执行请求给出明确说明**。

**改动**（全部在 CLI `crates/rsagent/src/main.rs`，保持库层 locale-free）：
- `Renderer` 增加 `cwd: PathBuf` 字段与 `Renderer::new(cwd)`（`main` 传 `cli.cwd`），用于判断文件是新建还是覆盖。
- 新增 `Renderer::describe_approval(tool_name, args) -> Vec<String>`：按工具类型生成中文说明。
  - `bash`：`执行一条系统命令：<cmd>` + 风险说明。
  - `write_file`：经 `cwd.join(path).exists()` 判断 → `新建文件：x` 或 `覆盖已有文件：x（原有内容会被替换）`，并给出字节数。
  - `edit_file`：`修改文件：x` + `改动：把「old」替换为「new」`（`quote()` 单行化 + 截断），文件不存在时附警告。
  - 其它：通用回退（工具名 + 参数）。
- 审批提示改为多行中文块：`? 需要你确认` / `  操作：…` / `  说明：…` / `  → 输入 y 再回车 = 允许执行` / `  → 直接回车 = 拒绝（我会换个方式继续）`。
- 新增自由函数 `describe_action(tool_name, args)`（`⚙` 行去 JSON 化，如 `⚙ 执行命令：echo hello`）、`tool_display_name()`（`✓`/`✗` 行用中文名，如 `✓ 读取文件：…`）、`arg_str()`、`quote()`。

**实测（真实模型，`--cwd` 指向临时目录）**：① bash 允许 → 中文说明 + 风险提示；② 新建文件 → `新建文件：brand-new.txt`；③ 覆盖已有 → `覆盖已有文件：existing.txt（原有内容会被替换）`；④ edit → `改动：把「hello」替换为「hi」`。四例均符合预期。

**结果**：`cargo fmt --check` 干净、clippy 0 告警、11 测试全过、doc 正常；README 同步更新为新提示样式。
