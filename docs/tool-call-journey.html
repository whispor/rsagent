一次工具调用的完整旅程 The Life of a Tool Call — from prompt() to AgentEnd

模型说"调用 word_count"之后，到底发生了什么？这张图把 Agent::run_turns 里一个完整回合拆成 11 步，标出每一步发生在哪一层、 调用哪个函数、以及发出哪些事件。所有名称都取自真实代码，不是示意。

实线 = 请求向下；虚线 = 事件向上。详见 docs/ARCHITECTURE.md §2 与 §4。

11 步旅程 · The Journey

  1. 1
    rsagent 你敲下一句话，循环被点亮

    Agent::prompt(input) 把输入包成一条 Message::user 推进对话记录， 重置取消令牌，然后交给循环。它只负责"开工"，不负责"收工"。

    发出 AgentStart MessageStart MessageEnd
  2. 2
    rsagent-agent 进入循环：置位、清错、准备收尾

    run_loop() 置 is_streaming = true、清空上一轮的 last_error，然后调用真正的核心 run_turns()。 无论成功还是失败，它都会在最后发一次 AgentEnd。

  3. 3
    rsagent-agent 每个回合的开场：插队消息 + 裁剪上下文

    run_turns() 每轮先做三件事：inject_steering() 把排队的插队消息写进对话记录；compact_context() 若超出模型上下文预算 （窗口的 3/4），就按整回合丢弃最旧的消息——首回合与最新回合永远保留， 且工具调用不会与它的结果被拆散；probe_health() 最后探一次各来源的健康（熔断器刚跳闸的来源会在此被点名，见右侧 SourceUnhealthy）。

    发出 ContextCompacted（仅在裁剪时） SourceUnhealthy（仅在跳闸时） TurnStart
  4. 4
    rsagent-agent rsagent-ai 组装请求，交给提供商

    stream_turn() 用 build_context() 打包： system prompt + 全部消息 + 每个工具的 ToolSpec。 然后 Models::stream() 按 model.provider 路由到对应 Provider，拿到一条 EventStream。

    给模型的永远是 ToolSpec（名称、描述、JSON Schema）， 不是工具本体——协议契约与执行逻辑因此能各自演进。
  5. 5
    rsagent-agent 边流边播：每个事件都转发给订阅者

    循环用 tokio::select!（biased，取消优先）同时等两件事： 取消信号与下一个 StreamEvent。收到 Start 就发 MessageStart；此后每一个流事件都原样包进 MessageUpdate 转发出去。终局事件（Done / Error） 用 terminal_message() 取出最终消息。

    发出 MessageStart MessageUpdate × N
  6. 6
    rsagent-agent 看停止原因，决定要不要调工具

    把 assistant 消息写进对话记录后，看 stop_reason：

    · Error / Aborted → 记入 last_error，发 TurnEnd，结束；
    · ToolUse 且带工具调用 → 进入第 7 步；
    · 其它 → 发 TurnEnd，有排队的 follow-up 就继续，否则返回。

    发出 MessageEndTurnEnd
    模型级失败（缺密钥、网络）会返回 Err(AgentError::ModelFailed)——CLI 靠它退 1。 而 Aborted（用户中断）才是那个「记入 last_error、 返回 Ok(())」的分支，所以 README 说中断退 0。
  7. 7
    rsagent-agent rsagent 预检与审批——顺序进行，且审批排在"开始"之前

    run_tool_calls() 先顺序预检每一个调用： check_approval() 若该工具 requires_approval() 且有审批器， 就先发 ToolApprovalRequest（仅当审批器真的要问用户）， 调用 approver.approve()，再发 ToolApprovalResponse。

    通过 → 发 ToolExecutionStart，进入待执行队列； 拒绝 → 直接生成一条"被审批策略拒绝"的工具结果。

    发出 ToolApprovalRequest ToolApprovalResponse ToolExecutionStart
    注释里写得很清楚：审批必须在 start 之前， 否则界面会先显示"开始执行"、再回头问"要不要执行"，是误导。
  8. 8
    rsagent-agent Tool 并行执行——除非批里有"必须顺序"的工具

    只要这一批里任何一个工具 is_sequential() 为真，整批顺序执行； 否则用 join_all 并行。每个调用走 run_one() → execute_one()：

    按 spec().name 找到工具（找不到就报 unknown tool）， 构造 ToolContext（工作目录 / 取消令牌 / 进度通道 / 路径围栏）， 然后 tool.execute(call_id, args, &context)。

    工具可发 ToolExecutionUpdate（进度）
  9. 9
    rsagent-agent 回收结果：截断、发事件、写回记录

    结果先过 truncate_result()——单条超过 32,000 字符就截断， 免得一次工具输出撑爆上下文。随后发 ToolExecutionEnd（带 content 与仅调用方可见的 details）， 从 pending_tool_calls 移除，再把 Message::ToolResult 写进对话记录并发 MessageStart / MessageEnd。

    发出 ToolExecutionEnd MessageStartMessageEnd
  10. 10
    rsagent-agent 回合收尾，然后回到第 3 步

    发 TurnEnd（带这一轮的 assistant 消息与全部工具结果）。 只有当每一个结果都要求终止时（terminate 全为真）才提前结束； 否则 continue——此时工具结果已经在上下文里，模型能看到它们， 于是产生新的回合。

    发出 TurnEnd
  11. 11
    rsagent-agent 运行结束

    run_loop() 复位 is_streaming、清空 pending_tool_calls，发出最后一条 AgentEnd，带上完整的对话记录。 至此返回值（结局）与事件流（过程）都到齐了。

    发出 AgentEnd

两条通道 · Two Channels

返回值 = 结局
prompt() 返回 Result<(), AgentError>。 只表达"跑完了没有"，不表达"模型说了什么"。
事件流 = 过程
每条 AgentEvent 经无界通道送到订阅者， 让 UI 能在另一个任务里边跑边渲染。

事件词汇表 · AgentEvent

  • AgentStart / AgentEnd整次运行
  • TurnStart / TurnEnd一个回合
  • MessageStart / End一条消息
  • MessageUpdate流式增量
  • ToolExecutionStart工具开跑
  • ToolExecutionUpdate工具进度
  • ToolExecutionEnd工具结束
  • ToolApprovalRequest请求审批
  • ToolApprovalResponse审批结果
  • ContextCompacted裁剪上下文
  • SourceUnhealthy来源熔断
